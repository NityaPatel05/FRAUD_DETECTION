# Synthetic payments world (Track C)

IEEE-CIS stays the main dataset for model accuracy. This is a **separate**, simulated
world for showing fraud components that IEEE-CIS cannot support, because it has no
customer, merchant, terminal, IP, device-id, AVS/CVC/3DS or chargeback-date fields.
It is never joined to IEEE rows and never used to balance or augment them.

```
venv/Scripts/python.exe scripts/run_simulator.py --out data/synthetic/v1      # ~1.36M rows, ~1 min + ~1 min validation
venv/Scripts/python.exe scripts/run_simulator.py --small --out data/synthetic/smoke
venv/Scripts/python.exe -m pytest tests/test_simulator.py -q
```

Output: `transactions.parquet`, `entities/`, `ground_truth/`, `metadata.json`,
`validation.json`, `data_card.md` (schema, splits, scenario table, fidelity and
leakage results). `data/synthetic/` is git-ignored; regenerate it from the seed.

## Why it is built this way

| Decision | Reason |
|---|---|
| Agent-based simulation, not CTGAN/TVAE/SMOTE | A generative model fitted to IEEE only reproduces IEEE: it cannot invent fields IEEE doesn't have. Oversampling doesn't raise AUC-PR for GBDTs and hurts calibration. |
| Fraud is generated by attacker agents | If labels were stamped on rows after generation, the "fraud signal" would be whatever the labelling rule used. Here the label is the process that produced the row. |
| Authorisation from mechanisms | CVC mismatch → N7, failed 3DS → 05, invalid PAN → 14, plus an issuer risk score on observable inputs. These rules apply to legit and fraud rows alike, so the decline code is not a disguised label. |
| Legit traffic is messy on purpose | Sessions of several purchases, travel, new phones, rotating home IPs, shared mobile and wifi IPs, VPNs, households sharing addresses, and friendly-fraud disputes. Without this, velocity or "new IP" would separate fraud trivially. |
| Random public ids | Accounts and devices created later (mules, gang devices) would otherwise get the highest ids, which is a leak. |
| A novel scenario only in the test period | `bust_out` is never seen while designing features. It is an honest test of "does it catch fraud we didn't design for". |
| Label delay | `label_date` is 1–120 days after the event (chargebacks take weeks). Label-history features must use what was known at the time. |

## Layout

| File | Role |
|---|---|
| `src/simulator/config.py` | `SimConfig`: size, horizon, splits, fraud-rate target, scenario shares |
| `src/simulator/geo.py` | countries, cities, MCCs, email/device mixes, synthetic IP blocks |
| `src/simulator/entities.py` | customers, cards, merchants and terminals, devices, IPs, households, contacts, trips |
| `src/simulator/legit.py` | legit behaviour (vectorised) |
| `src/simulator/scenarios.py` | attacker agents (`FraudFactory`): incidents are generated until each scenario's row budget is met |
| `src/simulator/auth.py` | AVS / CVC / 3DS and ISO 8583 response codes |
| `src/simulator/world.py` | orchestration, friendly fraud, label dates, public schema, `SimResult.save` |
| `src/simulator/validate.py` | fidelity vs IEEE aggregates, single-column leakage scan, scenario-signal AUCs, structure checks |
| `src/simulator/datacard.py` | renders `data_card.md` |

## Scenarios and the signal each one is meant to be caught by

| Scenario | Story | Designed-for signal |
|---|---|---|
| card_testing | Bursts of $0.5–5 online charges on one merchant; card lists or BIN enumeration | merchant / BIN velocity, decline-code bursts |
| stolen_card_cnp | Gang uses a compromised card online; shared gang devices and IPs | new device for the customer, IP vs card country, gang infrastructure reuse |
| account_takeover | New device and IP, email changed, stored card, P2P to mules | new device or email for the customer, then outbound P2P |
| terminal_cashout | Crew runs counterfeit cards through one terminal for 1–4 weeks | terminal fraud rate with label delay (Handbook) |
| skimming | Cards seen at a skimmed terminal are cloned and used elsewhere later | impossible travel; common point of purchase |
| mule_ring | Victims → entry mules → layering (chain, scatter-gather, gather-scatter, cycle, fan-out) → cash-out | device/IP shared across accounts, receiver fan-in, young accounts; `ring_id` for ring-detection rate |
| bust_out (novel) | Long-standing account maxes out on high-value goods from its usual device | spend vs own history (no identity anomaly at all) |
| friendly_fraud | Legit purchases later disputed | none: label noise |

## How to use it (later phases)

- Split by time with `metadata.json["splits"]`. Never shuffle.
- Do not use `GROUND_TRUTH_COLS` (`is_fraud`, `label_date`, `chargeback_date`, `fraud_scenario`, `incident_id`, `ring_id`) as features.
- Use `auth_response_code` and `approved` only from earlier rows. They are the result of the decision the model makes.
- The causal primitives in `src/feature_engineering/entity_ops.py` and `streaming_ops.py` work on this schema directly (`validate.py` uses them). `pipeline_v2` expects the IEEE schema, so this world needs its own feature path.
- Report results as "engineering demonstration on simulated data", never as real-world accuracy.
